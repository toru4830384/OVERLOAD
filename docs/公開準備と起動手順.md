# 公開準備と起動手順

この改修は `codex/integration-test` の a03546564cdaa0c97b75de5020e4f26d4313d167 を基準とする。作業ブランチは `codex/publication-auth`。GitHubへのpush・PR作成・クラウドへの配置は別工程であり、この文書の存在は公開完了を意味しない。

## ローカル起動

Java 17、Node.js 26、MySQLを使用する。既存DBを試しに移行せず、まずバックアップと復元試験を行い、新しい検証用DBで実施する。DBの作成や権限付与は管理者が対象を確認して行う。

資格情報は環境変数で渡す（`.env.example`参照）。シェル履歴・Git・スクリーンショット・ログへパスワードを残さない。設定ファイルにrootや空パスワードを既定値として置いていない。

```sh
cd backend
./gradlew test bootJar
cd ..
python3 tools/run-backend.py --spring.profiles.active=local
```

`local`プロファイルはlocalhostのHTTP動作用にSecure Cookieを解除する。公開環境には指定しない。フロントは別のターミナルで起動する。

```sh
npm ci
npm test
npm run lint
npm run dev -- --host 127.0.0.1
```

APIの既定接続先は127.0.0.1:8080。変更する場合は `OVERLOAD_DEV_API_TARGET` を指定する。OSのファイル監視が利用できない環境のみ `OVERLOAD_DEV_POLLING=1` を設定する。

### 起動中のJARを上書きしない

`backend/build/libs/` のJARを直接実行したまま再ビルドすると、遅延ロードされるクラスや入れ子JARを読めなくなり、要求の処理とエラーの記録まで失敗し得る。今回の調査で、実行中JARの上書き後に `NoClassDefFoundError: ch/qos/logback/classic/spi/ThrowableProxy` とHTTP無応答を再現した。

`tools/run-backend.py` は毎回新しい `.run/release-*/app.jar` へ物理コピーし、ZIPの整合性を検証し、SHA-256を記録して読み取り専用にした後、そのコピーを実行する。ビルド先・別の起動とはファイルを共有しない。新しいビルドを動かすには、旧プロセスを終了し、再度この起動処理を使う。実行中の `.run/` を削除・置換しない。これはPython実行環境で検証したローカル起動方法である。

本番も同じ原則で、バージョンごとの新しい配置先または固定ダイジェストのコンテナを使用する。稼働中コンテナへビルドフォルダーをマウントしない。アプリとDBのヘルスチェックを確認後に切り替え、旧リリースは停止まで保持する。

## 認証とデータ分離

- 登録: `POST /api/auth/register`。ログインIDは小文字英数字と `_` の3〜32文字。パスワードは15〜128文字。プロフィールは既存の共有制約に従う。
- ログイン: `POST /api/auth/login`。Argon2idで照合し、セッションIDとCSRFトークンを更新する。
- 本人確認: `GET /api/auth/me`。本人プロフィール: `GET/PUT /api/me`。
- ログアウト: `POST /api/auth/logout`。サーバー側セッションを無効化する。
- 変更要求は先に `GET /api/auth/csrf` で取得したトークンを返されたヘッダー名で送る。Cookieを同一オリジンで利用する。
- 個人データ要求はログイン結果の `accountKey` を `X-Overload-Account` に付ける。古いタブとCookieの本人が異なる場合409で拒否する。このキーだけで認証は成立しない。
- ワークアウト作成・取得の所有者はサーバーの認証情報から決定する。画面やJSONからユーザーIDを指定しない。旧 `/api/users/**` は公開しない。
- DBに保存するのはパスワードハッシュ。ログインIDの重複はDB一意制約とトランザクションで防ぐ。
- 旧匿名下書きは新しいアカウントへ自動で引き継がない。本人のIDと専用名前空間で分離し、旧下書き自体は消さない。

現在はメール認証、パスワード再設定・変更、退会・データ削除、アカウント回復窓口が未実装。長期の一般公開には、これらの運用とプライバシーポリシー、問い合わせ窓口の合意が必要である。

## 保存中の異常

初回の保存成功を通常の動作とする。自動で保存要求を再送しない。CSRF取得・応答本文の読込も含めて1操作20秒の期限を設ける。

期限切れや通信断で「DBへ保存されていない」と断定しない。保存結果は未確認と案内し、終了日時・UUID・送信内容と入力下書きを保持する。400/404/422の確定拒否だけ編集へ戻す。結果確認まで下書きを消さない。利用者が明示的に再送する場合に備え、既存のユーザーとUUIDの一意制約、同一内容の検証を維持する。これは障害からの回復策であり、保存待機の原因修正とは区別する。

## DB移行

Flyway V1:既存6表、V2:認証情報・JDBCセッション、V3:参照データ。空DBは起動時に順番に適用する。通常の業務ユーザーと移行用ユーザーを分ける場合は `OVERLOAD_MIGRATION_USER/PASSWORD` を使用する。業務用ユーザーの実行時権限は対象スキーマのSELECT/INSERT/UPDATE/DELETEだけとし、DDL権限を付けない。移行用資格情報を保持しない別ジョブへの分離は本番構成で行う。

既存DBに自動baselineしない。`clean`も無効。旧usersのID・履歴の所有者は変更せず、新規登録と結び付けない。

既存DBを移行する前に、DDLをV1と比較し、一意制約・snapshot列・文字コードを含めて一致を確認する。バックアップを別DBへ復元し、承認された移行担当が明示的にbaseline version 1を設定してV2以降を適用する。実データへのbaselineや資格情報の付け替えは、この作業では実施していない。マスター名の重複がある既存DBは、V3を適用する前に整理方針を確認する。

SQLの適用済みファイルは編集しない。変更は新しい番号で追加する。検証DBでの編集によるchecksum不一致を、本番の検証無効化で解消しない。

## 公開前の残工程

現在はカード登録なしというユーザー条件により、Render FreeとTiDB Cloud Starterの構成を選定している。詳細は「RenderとTiDBの公開手順.md」を参照する。以下のOCI案は当初の比較案。OCI Always FreeのVMへHTTPS終端・静的フロント・Java・MySQLを配置する構成も比較した。無料条件・回収条件・空き容量については別紙「公開調査と改修計画」の公式資料を確認する。無料の永続サービス保証はない。アカウント操作と課金を伴う操作はユーザーの事前確認を必要とする。

1. OCIリージョン、空き容量、対象アカウント、公開用ドメインと運用者を確定する。
2. MySQLの本番対応バージョンで移行・復元・権限分離を確認する。手元の結合テストはMySQL 9.6で実施しており、Flywayはこのバージョンを検証済みとしていない旨を警告している。
3. Caddy等でTLS証明書を自動更新し、同一オリジンの `/api` のみAPIへ転送する。MySQLとJavaのポートはインターネットへ公開しない。Secure/HttpOnly/SameSite CookieとCSRFを有効にする。CORSは必要なオリジンだけ明示し、ワイルドカードにしない。
4. プロキシで要求サイズ、ヘッダー・本文受信の期限、接続数、登録・ログイン制限を設定する。アプリのIP制限は接続元アドレス基準。インターネット越しのX-Forwarded-Forを無条件に信用しない。プロキシ経由での制限動作は本番環境で検証する。
5. DBの暗号化バックアップをVM外へ保存し、保持期間・世代数・容量上限を設定する。別の空DBへの復元と照合を定期実施する。アプリを旧版に戻してもDBを無断で巻き戻さない。
6. 5xx、応答時間、ログイン制限、ディスク残量、バックアップ失敗、証明書期限を監視する。ログには認証本文・Cookie・トークン・パスワード・個人メモを出さず、保存期間とローテーションを設定する。
7. 別ネットワークの実ブラウザから登録、初回保存、再取得、再ログイン、他人データの非表示を確認する。復旧手順と連絡先も確認してから公開完了とする。

ここに示した本番構成、HTTPS、バックアップ、外部監視、外部アクセスは未構築・未検証である。
